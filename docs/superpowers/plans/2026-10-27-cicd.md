# CI/CD: a deploy that takes under a minute

**Status:** APPROVED — implemented on 2026-10-27.

## Context

Deploying to the VPS means building a 2.6 GB Docker image and restarting the stack. A cold build
took **20 minutes** on this machine, and the goal is a deploy loop well under five minutes —
ideally under a minute — with as little manual work as possible.

The measurements below are from this repo, not estimates.

### Where the 20 minutes actually went

| Step | Size | Time | Notes |
|---|---|---|---|
| `apt-get install` (tesseract, CJK fonts, libgl) | 401 MB | ~1–2 min | Rarely changes → cached |
| `uv sync` for the worker (base + the `ocr` group) | 1.71 GB | ~5–8 min | Only changes when `pyproject.toml`/`uv.lock` change → cached |
| `COPY --from=deps-worker /app/.venv` | 1.71 GB | ~2–4 min | Re-exported every build |
| `RUN uv run python -m app.warmup` (model download) | 139 MB | ~3–5 min | **Re-downloaded on every app change** — the layer sat *after* `COPY app/`, so any code edit invalidated it |
| Everything else | ~1 MB | seconds | |

**The build was not slow because of the app — it was slow because of what it downloaded.** `paddle`
alone is 694 MB of the venv; janome's IPADIC is 137 MB; and we shipped **both** opencv flavours
(`opencv-python-headless` from the `ocr` group plus `opencv-contrib-python` from
`paddleocr[all]`) — 171 MB duplicated, and the headless build was shadowed anyway. (They also
share one `cv2/` directory: removing one uninstalls the other, which is how the duplicate was
noticed.)

## Decisions

| Choice | Value |
|---|---|
| Where the image is built | **In CI**, on GitHub's runners, and pushed to the registry |
| Registry | **GitHub Container Registry** — container storage is free, and the built-in `GITHUB_TOKEN` pushes it, so no extra secret |
| paddlepaddle source | **PyPI** — the wheel is there (cp312, manylinux x86_64) and the Chinese mirror is a single point of failure |
| OCR model weights | **Baked into the image**, in a stage of their own so a code change never invalidates them |
| Trigger | Push to `main` → test → deploy. Pull requests run the tests only |
| Server access | The VPS password is used **once**, to install a restricted deploy key. The CI never holds the password |

## The flow

```
push to main
   └─ GitHub Actions
        ├─ test:   pytest + ruff + pyright      (~2 min, no OCR stack needed)
        ├─ build:  web and worker, in parallel  (~2–4 min, cached between runs)
        │          → pushed to ghcr.io
        └─ deploy: ssh → the server            (~30 s)
                        git pull --ff-only
                        docker compose pull     ← only the changed layers
                        docker compose up -d
                        health check
```

**The server never builds and never downloads the dependencies.** The images are built on
GitHub's runners and the server pulls only the layers that changed — about a megabyte for a code
change, because the 2 GB dependency layer and the OCR weights are already in the registry.

This matters more than the seconds it saves: with the build on the server, a deploy competes with
the running app for the machine's memory and disk, and the first one has the site down for the
whole download. With the build in CI, the server only ever does I/O.

The running app keeps serving while the pull happens; only the final `up -d` restarts the
containers, which is a second or two.

## The Docker optimisations

1. **Move the model download into a stage of its own.** `RUN uv run python -m app.warmup` used to
   sit *after* `COPY app/ app/`, so every code change invalidated it and re-downloaded 139 MB.
   It is now a `models` stage, and the worker copies the finished weights out of it.
   **The stage copies only the four files the warm-up reads** (`app/warmup.py`, `app/core/ocr.py`
   and the two `__init__.py` files). Copying the whole `app/core/` directory instead ties the
   cached weights to every change inside it — that mistake cost a 15-minute rebuild.
2. **Drop the duplicate opencv.** `opencv-contrib-python` (from `paddleocr[all]`) already
   provides `cv2`; listing `opencv-python-headless` as well installed a second copy of the same
   library for nothing. −81 MB and one fewer wheel.
3. **Keep the `uv` binary out of the shipped images.** It lives in its own stage; the production
   images call `/app/.venv/bin/...` directly. −58 MB.
4. **Pin `ghcr.io/astral-sh/uv:latest`** to `0.9.17`. `:latest` makes the build unreproducible.
5. **Fix `.dockerignore`.** `worktools-data/` (root-owned runtime data) and `.sesskey` (a session
   credential) were gitignored but **not** dockerignored — they would have been shipped into
   every build context, and on CI that means a secret in the context.
6. **Switch paddlepaddle to PyPI** and re-lock. Fewer hosts to reach, and the wheel comes from a
   CDN that is fast from Japan too.
7. **Keep the `--mount=type=cache` on the uv cache** — the wheels stay on the server between
   builds, so a dependency change re-links without re-downloading.
8. **Never `--no-cache`.** The server's cache is the whole point.

### Measured result

| Build | Before | After |
|---|---|---|
| Cold (deps changed) | 20 min | **2 min 8 s** |
| Code-only change | 15 min (the weights re-downloaded) | **2.6 s** (one layer rebuilds) |
| Nothing changed | — | **1.8 s** |
| Worker image | 2.6 GB | **2.29 GB** |
| Web image | 442 MB | **383 MB** |

## The GitHub Actions workflow

`.github/workflows/ci.yml`, three jobs: `test`, `build` (a matrix over the two
image targets, so they build in parallel) and `deploy`.

**`test`** — on pull requests and pushes:
- `astral-sh/setup-uv`, then `uv sync --frozen` with the virtualenv cached against
  `uv.lock`. The environment is the full one, OCR stack included: the type check has to
  resolve numpy, cv2, paddleocr and paddlex, or it reports them as missing imports. Only
  the first run pays for the download.
- `uv run pytest`, `uvx ruff check .`, `uv run pyright app/` — all three are clean, so the
  gates are real.

**`build`** — on pushes to `main`, after `test` passes:
- `docker/setup-buildx-action` and `docker/login-action` against `ghcr.io`, using the
  workflow's own `GITHUB_TOKEN` — no extra secret.
- `docker/build-push-action` per image target, tagged with the commit and `latest`, with
  `cache-from/cache-to: type=gha` so the heavy layers survive between runs.

**`deploy`** — on pushes to `main`, after the images are pushed:
- SSH to the server with the key from the secrets and run the fixed deploy command.
- The key is restricted on the server with a **forced command**, so the runner can only run the
  deploy script — a leaked key cannot do anything else.

Plain `ssh` rather than a third-party action: fewer moving parts, and no third-party code in the
path that holds the deploy key.

## The server-side deploy script

`scripts/server-deploy.sh`, installed on the VPS as `/usr/local/bin/deploy-workutils`:

```bash
git pull --ff-only
export IMAGE_TAG="$(git rev-parse --short HEAD)"
docker compose --profile production pull
docker compose --profile production up -d --remove-orphans
# then wait for the app to answer
```

The pull happens **before** `up -d`, so a failed pull leaves the running containers untouched and
still serving. If the new containers do not come up, the previous image is still in the server's
Docker cache and a rollback is `git checkout <old-sha> && docker compose up -d` — seconds, not a
rebuild.

The images are tagged with the commit they were built from, so a rollback is a matter of
re-tagging rather than rebuilding.

## What the server needs (set up once, outside CI)

- The deploy script installed at `/usr/local/bin/deploy-workutils`.
- A checkout of the repo at `/opt/work-utils`, on `main`, with a **read-only** GitHub key so
  `git pull` works.
- The `.env` with `JR_PASSWORD` and the other settings — on the server, never in git.
- `~/.ssh/authorized_keys` with the runner's public key restricted:
  `command="/usr/local/bin/deploy-workutils",restrict ssh-ed25519 AAAA... deploy`

## Secrets in GitHub

| Secret | What it is |
|---|---|
| `VPS_HOST` | The server's address |
| `VPS_USER` | The user the key belongs to |
| `VPS_SSH_KEY` | The private key the runner uses |
| `VPS_KNOWN_HOSTS` | The server's host key, pinned |
| `VPS_KNOWN_HOSTS` | The server's host key, pinned |

`known_hosts` is pinned rather than fetched with `ssh-keyscan` at deploy time, which would trust
whatever answers.

## Verification

- `uv lock` after the index change, then run the OCR over a real page: 52 regions, identical
  text — the PyPI wheel behaves the same as the mirror's.
- Build twice: the second build reuses the cached layers and finishes in seconds.
- A code-only change rebuilds one layer; the weights are not downloaded again.
- The workflow: a push to a branch runs the tests only; a push to `main` runs the tests and then
  the deploy.

## Risks

| Risk | Mitigation |
|---|---|
| The server's build fails (network, disk) | The build runs before `up -d`, so the running containers are untouched and the CI reports the failure |
| The runner's SSH key leaks | The key is restricted on the server to one forced command |
| The server's disk fills with old layers | `docker image prune` and `docker builder prune` on a weekly cron |
| PyPI's paddlepaddle wheel differs from the mirror's | Verified by running the OCR over a real page after re-locking; the mirror is one `pyproject.toml` edit away |
