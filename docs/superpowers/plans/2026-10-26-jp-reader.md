# JP Reader: OCR a Japanese physics book, tap a word, get its reading

**Status:** APPROVED — not started. Ready to implement from this document.

## Context

Learning Japanese from a physics book currently means: photograph a page with Google Lens on the
Android phone, manually highlight a word, then manually copy it into Google Translate or a
dictionary. Every lookup repeats the same steps, and nothing is shared between phone and laptop.

Target workflow: one web app the phone and the laptop both talk to. Photograph a page → OCR → see
the full text and its translation with clickable regions over the image → tap a region, pick the
words you care about → get **kana furigana** (the "how to read") plus a translation → save that
phrase so it is on both devices.

This repo already has the hard parts: FastAPI + FastHTML, Redis, TaskIQ, a worker with PaddleOCR
models warmed into the Docker image, and a Tesseract → Google Translate pipeline. The new tool
reuses that plumbing instead of adding a stack.

### User requirements (from the original session)

- Capture an image on the Android phone, upload it to the app.
- Show the **full text** and **the translation**.
- When a phrase is highlighted, show **how to read** it.
- Accessible from both the Android phone and the work laptop.
- **MVP:** store in Redis, cap the number of images kept at once.
- Writes require a hard-coded/env password; reads are public
  (list images, image detail, get/post the selected phrase/expression).
- KISS, DRY, MVP first.

## Decisions

| Choice | Value |
|---|---|
| OCR engine | **PaddleOCR**, plain text pipeline, `lang="japan"` (det + rec, 133 MB, already cached) |
| Where OCR runs | **TaskIQ worker** — the web process stays free of OCR work |
| "How to read" | **Kana furigana** (HTML `<ruby>`), offline, via **Janome** (pure Python, IPADIC bundled) |
| Auth | **Password required for writes** (upload, save selection). GETs public. `X-JR-Password` header or form field |
| Storage | **Redis** — metadata + image bytes, capped at N images, oldest evicted first |
| Record id | **`uuid.uuid4().hex`** — see "Identifier choice" below |

### Alternatives considered and rejected

- **Android app with on-device OCR** — no cross-device access, no server-side dictionary, far more
  code than a FastAPI tool. The phone already has a good camera and browser.
- **Keep using Google Lens + a notes app** — the manual copy step is exactly the pain being removed.
- **PaddleOCR `PPStructureV3`** (already in the repo) — it OCRs *per layout-region crop*, so its
  coordinates are local to each crop, not page-global. The plain pipeline returns `rec_boxes` in
  original image space, which is what the overlay needs.
- **Word-level OCR boxes** (`return_word_box=True`) — verified: for Japanese it splits *kanji into
  single characters* while gluing kana runs together, so it is useless for word selection. Word
  chips are derived from Janome tokens of the tapped line instead.
- **Per-region translation fan-out** — a 40-region page would make 40 calls to the free Google
  Translate endpoint and get rate-limited. One whole-page call + on-demand phrase calls instead.

### Identifier choice: `uuid4` vs `uuid7` vs `cuid2`

Evaluated, because the record id is the only access control on the public GET endpoints.

| Option | Entropy | Sortable | Needs a new dependency? | Verdict |
|---|---|---|---|---|
| `uuid.uuid4().hex` (current) | 122 random bits, no timestamp leak | no | no | **Chosen** |
| `uuid.uuid7()` | 48-bit ms timestamp + 74 random bits | yes | **yes** — stdlib only from Python 3.14; this repo is pinned to 3.12 (`requires-python = ">=3.12"`, `python:3.12-slim`) so it needs the `uuid6` package | rejected |
| `cuid2` (v2.1.0) | timestamp + counter + random | yes | **yes** — zero-dep package, but a new dep | rejected |

Why `uuid4` wins here:

1. **Ordering is already solved.** The only thing a time-ordered id buys is chronological sorting,
   and `jr:index` is a sorted set scored by `created_at` — the ordering requirement is met
   explicitly, so the id's sortability would be redundant.
2. **Max entropy matters more than sortability.** Every GET endpoint is public and keyed by the id,
   so "unguessable" outranks "sortable". `uuid4` gives 122 random bits and leaks nothing;
   `uuid7` embeds the creation millisecond and `cuid2` a counter+timestamp prefix.
3. **No new dependency for zero functional gain.** Both alternatives are small, maintained,
   zero-dependency packages — but they buy nothing this app needs today.
4. **Repo consistency.** `uuid.uuid4().hex` is already the convention in three places
   (`image_translator/router.py:51`, `image_downloader/router.py:222,260`, `core/files.py:13`).

**Revisit when:** the app moves to Postgres (`PROJECT_REQUIREMENTS.md` names NeonDB as the future
store). A UUIDv7 primary key then genuinely helps — sequential inserts avoid B-tree page splits.
At that point the swap is one line plus a dependency.

## Architecture

```
phone / laptop browser
        │  POST /api/jp-reader/upload          (multipart, X-JR-Password)
        ▼
   web process ──── normalizes photo (EXIF, ≤2000px, JPEG q90) ──► Redis DB4
        │  writes jr:{id}:image (bytes) + jr:{id} (JSON record, status=pending)
        │  writes task:{id}:progress (Redis DB3, reused store)
        │  .kiq() ──────────────────────────────────────────────┐
        ▼                                                        ▼
   SSE /events/{id}                                    worker: ocr_page_task
   (polls task:{id}:progress)                            ├─ PaddleOCR → regions[]
        │                                                ├─ Janome → per-region tokens+readings
        │                                                ├─ 1× Google Translate → full-page translation
        ▼                                                └─ writes jr:{id} (status=done)
   GET /records/{id} ──► image + overlay boxes + full text + full translation
   POST /records/{id}/selections (X-JR-Password) ──► furigana + translation, stored in jr:{id}
```

One id (`uuid.uuid4().hex`) is used for the task, the record, the image blob and the SSE stream.

**Key split:** the worker owns OCR + the full-page translation (expensive, network-bound). The web
process owns furigana + per-phrase translation (fast, on demand). The browser never computes
anything about Japanese itself.

## Redis layout (new DB 4, prefix `jr:`)

| Key | Type | Value | TTL |
|---|---|---|---|
| `jr:{id}` | string | JSON record (below) | `JR_TTL_DAYS` |
| `jr:{id}:image` | string | normalized JPEG bytes | `JR_TTL_DAYS` |
| `jr:index` | zset | member `{id}`, score = created_at epoch | none |
| `task:{id}:progress` | string | **existing** store, `app/core/progress.py`, DB 3 | 7 days (existing) |

Record document:

```json
{
  "id": "9f2c…", "created_at": 1761470000.1, "status": "pending|ocr_running|done|error",
  "width": 1496, "height": 2000, "n_bytes": 284119,
  "text": "…full page text…",
  "translation": "…full page translation…",
  "regions": [
    { "i": 0, "bbox": [15, 30, 412, 102], "text": "力学の基本原理", "score": 0.954,
      "tokens": [ {"surface": "力学", "reading": "りきがく", "base": "力学", "okurigana": "", "ruby": true} ] }
  ],
  "selections": [
    { "id": "s1", "created_at": 1761470100.0, "region_indexes": [0], "phrase": "力学の基本原理",
      "ruby_html": "<ruby>力学<rp>(</rp><rt>りきがく</rt><rp>)</rp></ruby>…",
      "translation": "Basic principles of mechanics" }
  ]
}
```

JSON is written with `ensure_ascii=False` (Japanese must not be `\uXXXX`-escaped).

Eviction: after each upload, while `ZCARD jr:index > JR_MAX_IMAGES`, pop the oldest member
(`ZRANGE jr:index 0 0`), delete `jr:{id}` + `jr:{id}:image`, `ZREM` it. **Skip records whose
status is not terminal** (`done`/`error`) so an in-flight OCR is never evicted mid-flight.

## API (`app/tools/jp_reader/router.py`, prefix `/api/jp-reader`)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/upload` | **password** | multipart file → `{id}`; normalizes + stores + enqueues OCR |
| GET | `/events/{id}` | public | SSE, polls `task:{id}:progress` (copy of `image_translator/router.py:78-114`) |
| GET | `/records` | public | newest-first list (id, created_at, size, counts) |
| GET | `/records/{id}` | public | full record (regions, tokens, text, translation, selections) |
| GET | `/records/{id}/image` | public | the normalized JPEG bytes |
| POST | `/records/{id}/preview` | public | `{phrase}` → furigana + translation, **not** saved |
| POST | `/records/{id}/selections` | **password** | `{phrase, region_indexes?}` → furigana + translation, stored |
| GET | `/selections` | public | every saved selection across records (study list) |
| DELETE | `/records/{id}/selections/{sid}` | **password** | remove a selection |

`POST /records/{id}/selections` computes furigana + translation **server-side**; the client never
sends readings. The `preview` endpoint was added during implementation so the meaning of a phrase
shows up before it is committed, without writing anything.

## Pages

Two FastHTML pages, both under the jp-reader tool:

| Page | Purpose |
|---|---|
| `/jp-reader/` | Pick a photo → preview → password → upload with a progress bar (cancelable) → redirect to the detail page. Lists recent pages. |
| `/jp-reader/{record_id}` | The scanned page: live OCR progress, then the image with clickable regions, the full text and translation, the word chips and the saved phrases. "← New photo" and "Copy link". |

The detail page is addressed by the record id, so its URL is shareable: open it on the laptop
while the phone's upload is still being read and it follows the same progress, then shows the
same page. Progress is delivered over SSE — already the pattern in this repo, and it survives
page loads and reconnects, which polling would not.

Uploads use `XMLHttpRequest` rather than `fetch` because only XHR reports upload progress.

## Live updates between devices

Scans and saved phrases are published to a Redis channel (`jr:events`). `GET /api/jp-reader/stream`
follows that channel over SSE, so every open page learns about changes made elsewhere: a page
scanned on the phone appears on the laptop without a refresh, marked with a **New** badge that
fades after 20 seconds.

Events: `created` (a scan started), `updated` (the scan finished), `selection` (a phrase was
saved), `translated` (a translation arrived).

## Translation cache and pending state

Translations are cached in Redis (`jr:tr:{lang}:{sha256(phrase)}`, 30-day TTL), so the same
phrase is only ever translated once.

The preview and save endpoints return the **reading immediately** — it is computed locally by
Janome — and fetch the translation in the background. The response carries
`translation_pending: true`, and the client shows a spinner until the `translated` event
arrives. A cached phrase comes back complete at once.

MyMemory answers short words in a dictionary form (`[でんし] /electron/`); the reading is shown
separately, so the wrapper is stripped to just the meaning.

## Implementation notes

### OCR backend (`app/core/ocr.py`)

```python
PaddleOCR(
    lang="japan",
    use_doc_orientation_classify=False,   # else it downloads the doc-orientation model
    use_doc_unwarping=False,              # else it downloads UVDoc
    use_textline_orientation=False,       # else it downloads the textline-orientation model
)
```

With all three off, only det + rec (133 MB) are needed. Result extraction:

```python
for res in engine.predict(image):
    for box, text, score in zip(res["rec_boxes"], res["rec_texts"], res["rec_scores"]):
        x1, y1, x2, y2 = (int(v) for v in box)   # rec_boxes = axis-aligned [l,t,r,b]
```

`rec_boxes` are in **original image coordinates** — which is exactly the stored image, because the
web process normalizes before storing.

**`predict()` must be fed a numpy BGR array, never a PIL image** (`ReadImage` raises `TypeError` on
PIL). Use `cv2.imdecode(np.frombuffer(jpeg_bytes, np.uint8), cv2.IMREAD_COLOR)` —
`np.array(pil_img)` gives RGB and swaps the colour channels.

`paddlex` gates on `opencv-contrib-python` via `@class_requires_deps`, so a missing dep turns
`OCRResult` into a class that raises on instantiation. Guard explicitly in `app/core/ocr.py`:

```python
from paddlex.utils.deps import is_dep_available
if not is_dep_available("opencv-contrib-python"):
    raise RuntimeError("jp_reader requires opencv-contrib-python (pulled in by paddleocr[all])")
```

### Image normalization (web process, `service.py`)

```python
img = ImageOps.exif_transpose(Image.open(BytesIO(raw))).convert("RGB")
img.thumbnail((max_dim, max_dim), Image.LANCZOS)      # never upscales
img.save(buf, format="JPEG", quality=90, optimize=True)
```

EXIF transpose is **required** — phone photos carry an orientation tag and `PIL` does not apply it,
so without it the stored image and the OCR coordinates disagree with what the user sees.
Normalizing here (not in the worker) keeps the stored bytes and the OCR'd bytes identical, so the
browser's percentage overlay lines up exactly.

### Furigana (`app/core/japanese.py`)

Janome's `Token.reading` is **katakana**; unknown words give `'*'`. Rules for a token:

1. unknown (`reading` empty or `'*'`) → no ruby;
2. surface contains no kanji (U+4E00–U+9FFF) → no ruby (kana/latin/digits read the same);
3. otherwise → strip the trailing kana run from the surface to get `base` + `okurigana`, and drop
   the same number of characters from the end of the reading to get the ruby text.

```
読む → 読(よ)む      見る → 見(み)る      勉強 → 勉強(べんきょう)
切り → 切(き)り      力学 → 力学(りきがく)
```

Ruby HTML is built as a plain string
(`<ruby>base<rp>(</rp><rt>reading</rt><rp>)</rp></ruby>`) since it is returned inside a JSON
field, not rendered by FastHTML's component tree.

### Frontend

- `<input type="file" accept="image/*" capture="environment">` → opens the phone camera. Works over
  **plain HTTP** (unlike `getUserMedia`, which needs a secure context).
- Overlay: `<div class="relative">` + `<img class="w-full block">` + one absolutely positioned
  `<button>` per region with `style="left:12.5%;top:30.1%;width:20%;height:4%"` — percentages of
  the stored image, so it scales on any screen.
- Chips: the tapped region's `tokens[]` from the record, each rendered with its furigana; tapping a
  chip appends its surface to the phrase. Chips are built from Janome tokens, not OCR word boxes.
- The saved phrase is sent to the server; the server recomputes furigana + translation and returns
  the stored selection.
- JS lives in `app/static/jp-reader/reader.js` (a real file, not a Python string) and is loaded with
  `Script(src="/jp-reader/reader.js")`. FastHTML's static route is registered **first** and matches
  `/{fname:path}.{ext:static}` — so any `@rt` path ending in `.js` would be shadowed (none exist).
  `.js` is an allowed extension ✓.

## Risks

| Risk | Mitigation |
|---|---|
| Free Google Translate rate-limits | The worker makes **one** full-page call; phrase translations are on-demand and short. No per-region fan-out. |
| `uv.lock` not regenerated | Docker's `uv sync --frozen` fails — commit the lockfile. |
| `import cv2` in the web container | `opencv-contrib-python` (non-headless) needs `libgl1` → added to the web stage. |
| `static_path="."` leaks files from the CWD | Repointed at `app/static/`. |
| EXIF rotation ignored → overlay misaligned | `ImageOps.exif_transpose` in normalization. |
| `JR_PASSWORD` unset | Writes fail closed with a clear 503; GETs still work. |
| Password travels over plain HTTP on the LAN | Acceptable for a home LAN; it is never echoed back into the HTML and never prefilled. |
| Image ids are `uuid4().hex` | Effectively unguessable, which is what makes the public GETs acceptable for a personal tool. |
| `paddleocr[all]` ships the whole stack into the web image | Out of scope: splitting dependency groups per Docker stage is a separate change. |

## Out of scope for the MVP

- PWA manifest / "add to home screen" on Android.
- Deleting images manually (eviction is automatic by the cap).
- Romaji transliteration (kana furigana only, for now).
- Per-region translations (the full-page translation plus on-demand phrase translation covers it).
- Multi-page / multi-image documents (one page per upload).

## Improvements round (2026-10-27)

From `nihongojouzoimprove.md`. The full brief was judged too heavy for a personal tool; the
high-value subset was built. Plan: `~/.claude/plans/please-look-at-nihongojouzoimprove-md-frolicking-melody.md`.

**Shipped**

- Upload guards: a non-image is a 400, an over-40-megapixel image a 413, a truncated file a 400.
- Per-stage timings on the record and a collapsible "Processing details" panel.
- Active selection styling: default / hover / active / focus are distinct, and the tapped line's
  chip and saved phrase are highlighted.
- A base image that is never re-encoded, a revision counter, and an epoch guard so a slow job
  cannot overwrite a newer correction.
- Rotation controls (±90/180, fine ±0.1°), applied on the server so the overlay stays aligned.
- Region OCR: drag a box over text the detector missed and read just that area.
- An orientation suggestion from `PP-LCNet_x1_0_doc_ori` (6.9 MB), offered and never applied.
- Manual perspective correction with four draggable corners.

**Deviations**

| Planned | Shipped | Why |
|---|---|---|
| Corners in the base image's space | Corners in the **rotated** image's space; `GET /records/{id}/stage/rotated` serves that intermediate image for the editor | The perspective step consumes the rotated image, so the corners have to be measured there |
| Region box "in viewer coordinates" | Normalised to **0..1** of the image | Does not depend on how the viewer is scaled |
| `cv2.getPerspectiveTransform` | **Pillow's `Image.transform(..., QUAD)`** | The web process applies corrections and does not install the `ocr` group where opencv lives |
| — | The orientation classifier runs **standalone** | The pipeline discards the confidence and rotates the image under us, breaking the coordinate invariant |

**Verified**

- A 90° rotation of a real page: 52 → 53 regions, 46 of 51 lines read identically, and the base
  image is byte-identical afterwards (no cumulative resampling).
- The orientation model reads 0/90/180/270 at ~92% confidence.

### The image editor (reworked after the first round)

The correction panel became a real editor, in the style of an image tool:

- **"Edit image (optional)"** — a collapsible card, available as soon as the page
  exists, so a photo can be straightened *while* the first read is still running.
- **A live preview.** The canvas shows the uncorrected page with the change applied
  as you drag the slider — a CSS turn, and the quad as a clip. Applying sends it to
  the server, which produces the authoritative image.
- **The slider** replaces the angle buttons as the main control; the ±90°/180°
  presets stay, with ±0.1° fine steps and a numeric field.
- **The corners show the area**, not just four handles: the quad is drawn filled, so
  you can see the square that will be kept, and the handles are dragged inside it.

**The corners moved to the base image's space**, and the server now squares the page
*before* turning it. That makes the corners independent of the angle — a turn no
longer invalidates them — and it matches the preview, which clips and then turns.

**A correction is allowed while a read is running.** The epoch guard already drops the
older job's result, so the two cannot fight over the page; the older job is simply
wasted work. The 409 is kept for the retry endpoint, where a second queue really
would be pointless.

### The page reader rework (2026-10-27)

From `nihongojouzoimprove.md`. The brief is thorough but sized for a team; the high-value
subset was built, in small commits:

- **Save phrases removed** — reading the page is the point, collecting it is not.
- **Both pages server-rendered** — the detail page's structure moved from JavaScript into
  `views.py`, so a reload mid-read still shows the picture, and the page and a
  `/fragment` endpoint share one renderer.
- **The upload page can straighten a photo** — the same rotation controls, a live browser
  preview, and the angle travels with the upload so the page is stored already straight.
  The base stays unrotated, so it can still be corrected later.
- **The read is two jobs** — read the text, then translate it — so the text is readable
  while the translation runs. Measured on a real page: queue 0.2 s, OCR 9–13 s, translate
  15 s.
- **The page list has previews**, made once when the page is read.
- **The original and the translation side by side** — the translation is painted over each
  line, the way a translation overlay does. The lines go out as a numbered list in one
  request and the answers are split back up.
- **The region reader says what it found** instead of leaving the reader guessing.
- **Bigger uploads** — 200 MB, 80 megapixels.

The font helpers moved out of the image translator into `app/core/render.py`, which both tools
use, so "draw text that fits" has one implementation rather than two.

### The interface fixes (2026-10-28)

Five things were broken in the reader, all found by looking at the rendered page rather
than the source:

- **The two panes were not side by side.** The wrapper had lost its grid class, so the
  page and its translation stacked. The `lg:col-start-2` on the second pane pointed at a
  column that did not exist.
- **The boxes had no border and the tapped line was not marked.** The styles used
  `var(--p)`, which is DaisyUI 4's shorthand; DaisyUI 5 calls it `--color-primary`, so
  every `color-mix` was invalid. The reader's styles now live on the reader's page, with
  the right variable.
- **The page previews were broken for older pages.** A thumbnail is only made when a page
  is read, so pages read before that feature answer 404. The missing preview is now
  hidden rather than shown as a broken image.
- **The straighten controls were on the upload page before a photo was chosen.** They now
  appear with the photo.
- **Tapping a line appeared to do nothing.** The words of the tapped line were inside the
  collapsed "Details" section; they now sit under the image. The selected line and the
  typed phrase also survive the body being swapped in when the read finishes.

The page now renders its body server-side rather than leaving it empty for the script to
fill in, so a reload shows the picture straight away.
